# MultiParity tutorials: scripts for approval

Eleven short videos, about 60 to 90 seconds each.

- **Voice:** fal ElevenLabs v3, voice `5OhY6eII5od0GRAOSINf`.
- **Audio tags:** the `[tags]` are ElevenLabs v3 audio tags. They are used lightly, so the voice sounds like a person showing a coworker, not a narrator.
- **On screen:** a real recording with a visible cursor. It uses the made-up Cinder Works studio from the website: Alice, Mara, the Emberfall project and the Harbor DLC project.
- **Callouts:** GLSL clips on the Kitlig timeline. They are listed under each script with what they point at.
- **Shared callout styles:**
  - *ring*: a pulsing ring on a button.
  - *spot*: dims everything except one area.
  - *tag*: a short label that slides in next to something.
  - *sweep*: a light sweep across a row.

## 1. Getting set up

**On screen:** desktop app, Accounts, sign in, Projects, Sync to this computer, choose a folder.

> [warmly] Hey. This is MultiParity, and this one's about getting you set up. It takes about a minute.
>
> Open the app and go to Accounts. Type in your studio's server address, your email and your password, and hit Sign in.
>
> Now go to Projects. [curious] See Emberfall there? That's a project your studio already made. Click Sync to this computer.
>
> It asks where you want the files. Pick any folder you like. Your D drive, an external drive, wherever there's room. Click Sync this folder...
>
> [short pause] and that's it. The files come down, and from now on the app keeps that folder up to date for you.
>
> [lightly] Working with more than one studio? Just add another account. Every project from every account shows up in the same list.

**Callouts:** ring on *Accounts*. Tag "Your studio's server" on the address field. Ring on *Sync to this computer*. Spot on the folder picker. Tag "Any folder, any drive".

## 2. Starting a brand-new project

**On screen:** web Admin > Projects > New project, then the desktop app syncing a folder that already has files, Check the folder, everything shown as New, right-click > Ignore on autosaves, and the first publish.

> [friendly] Starting something new? Or bringing over a project that's just been sitting in a folder? Here's how to set it up.
>
> First, someone with admin rights makes the project. In the web app, go to Admin, Projects, and click New project. Give it a name, pick your organization, and click Make project. [lightly] It already comes with sensible rules for junk files, like autosaves and engine caches.
>
> Now, on the computer that has the files, open the desktop app. The new project's right there. Click Sync to this computer, and choose the folder your files are already in.
>
> [reassuring] Don't worry, nothing in that folder gets deleted or replaced. Click Check the folder if you want to see exactly what it'll do first.
>
> Everything shows up in Your work as New. Before you publish, have a quick look for stuff that shouldn't go up. Renders, backups, that kind of thing. Right-click it, choose Ignore, and pick how wide the rule should be. Just this file, or every file like it.
>
> Then tick it all, write "First version", and Publish. [pleased] That's your project. Now everyone else just clicks Sync to this computer and gets the lot.

**Callouts:** ring on *New project*. Tag "Admins only". Spot on the starter-rules note. Ring on *Sync to this computer*. Tag "Nothing gets deleted". Ring on *Check the folder*. Sweep on the New rows. Spot on the Ignore menu, tagged "Keep junk out". Ring on *Publish*.

## 6. Checkpoints: save points for you

# Running your own server

Eight videos for whoever deploys and looks after the server. They use the same voice, but with fewer tags and a bit more pace: this audience wants the commands.

**On screen:** a terminal and an editor beside the browser. The commands are typed live, at a readable speed, on a clean demo machine. Real secrets never appear; every password and key shown is a placeholder.

**Extra callout:** *code*, which highlights one line in the terminal or in `.env` and puts a label next to it.

---

## S1. A server in five minutes

**On screen:** `git clone`, `cp .env.example .env`, edit four settings, `docker compose up -d`, then sign in in the browser.

> [friendly] Let's get a MultiParity server running. All you need is a machine with Docker and some room for files.
>
> Clone the repo, go into it, and copy the example settings file to `.env`.
>
> Open `.env`. There are only four things you have to fill in. The admin's email and password, for you. A long random password for the database. You'll never type that one, so make it ugly. And the public URL, which is the address people will actually use to reach this machine.
>
> Then `docker compose up -d`. [short pause] That starts the server and its database.
>
> Open that address in a browser and sign in with your admin email. [pleased] Your first organization is already there. Next stop is Admin, to make a project and invite people.

**Callouts:** code on `MP_ADMIN_EMAIL` and `MP_ADMIN_PASSWORD`, tagged "You". Code on `POSTGRES_PASSWORD`, tagged "Long and random". Code on `MP_PUBLIC_URL`, tagged "The address people use". Ring on the sign-in button.

---

## S2. Where the files live

**On screen:** the `MP_STORAGE` lines in `.env`, then Admin > Projects, moving a project to another location.

> [thoughtful] Before your team starts throwing gigabytes at this, decide where the files go.
>
> By default it's a Docker volume on the server. That's fine to start with.
>
> If you've got a NAS or a big second drive, set storage to `mount` and point it at that folder. [reassuring] If that drive ever isn't there, the server refuses to start, instead of quietly filling up your system disk.
>
> Or use `s3`, which works with Backblaze, Cloudflare R2, Wasabi, AWS, or the MinIO that comes bundled.
>
> You can also have more than one location, say the NAS for active projects and a bucket for finished ones, and move a project between them from Admin, Projects. People keep working while it moves.

**Callouts:** code on `MP_STORAGE=local`. Tags "local", "mount" and "s3" slide in one by one. Code on `MP_STORAGE_LOCATIONS`. Spot on the move dialog, tagged "Live, no downtime".

---

## S3. Working from anywhere

**On screen:** a table of the options, then a Tailscale address and the Caddy `.env` lines.

> [casual] In the office, the plain address works. From home, the server has to be reachable over HTTPS. There are a few ways to do that. Pick one.
>
> Tailscale is the easiest for small teams. Everyone installs it, joins your network, and nothing is on the public internet at all.
>
> A Cloudflare tunnel is good when contractors shouldn't have to install anything. No open ports.
>
> Or, if the machine has a public address, use the built-in Caddy. Set your domain and an email in `.env`, start it with the `https` profile, and it gets a certificate by itself and keeps it renewed.
>
> [lightly] Oh, and file size doesn't matter here. Files travel in small parts, so proxy upload limits never get in the way.

**Callouts:** spot on each row of the table in turn. Code on `MP_DOMAIN` and `MP_TLS`. Code on `--profile https`. Tag "Certificates handled".

---

## S4. Backups, and getting them back

**On screen:** `MP_BACKUP_TARGET`, Admin > Fixing with Back up now, then the restore commands.

> [serious, but warm] Okay, the boring one that saves your studio someday.
>
> The server backs itself up every night: the database and every file. And it only copies what's new, so even a huge studio backs up fast.
>
> Out of the box it backs up to the same disk, which protects you from mistakes but not from that disk dying. So point `MP_BACKUP_TARGET` somewhere else, like a second drive, a NAS, or a bucket off site.
>
> You can see the last backups in Admin, Fixing, and there's a Back up now button. Hit it before any big change.
>
> Restoring is a few commands: stop the server, start an empty database, run restore, start it back up. [reassuring] It's all in the backup docs, and it's been tested end to end.

**Callouts:** code on `MP_BACKUP_TARGET`, tagged "Somewhere else!". Ring on *Back up now*. Sweep on the backup list. Code on `mp-server restore`.

## S5. Email

**On screen:** the SMTP settings in `.env`, then Admin > Fixing > Email and Send me a test email.

> [friendly] Email is optional, but it makes life nicer.
>
> With it, invites go out by themselves, people can reset their own passwords, and they get a heads-up when someone asks for a file they've claimed. You also get told if a backup fails.
>
> Set who it's from, then either your SMTP details or a SendGrid key. [aside] For Google or Microsoft, that's usually an app password, not your real one.
>
> Restart, go to Admin, Fixing, Email, and click Send me a test email. If anything's wrong, it shows you the provider's actual error, which is a lot more useful than "it didn't work."

**Callouts:** code on `MP_EMAIL_FROM`. Code on the SMTP block, tagged "Or SendGrid". Ring on *Send me a test email*.

## S6. Updating

**On screen:** Back up now, `git pull`, `docker compose up -d --build`, then a desktop app showing "Restart to update".

> [casual] Updating takes two commands.
>
> First, take a backup. Admin, Fixing, Back up now. [lightly] Every time. Future you will thank you.
>
> Then `git pull`, and `docker compose up -d --build`. The database updates itself when the new server starts.
>
> And the desktop apps? You don't have to do anything. They check your server for updates and offer "Restart to update" on their own. Updates are signed, so they only install genuine builds.

**Callouts:** ring on *Back up now*. Code on the two commands. Ring on *Restart to update*. Tag "Signed updates".

---

## S7. Hooking it into your pipeline

**On screen:** Admin > Fixing > Webhooks, add one and Send a test, then `mp watch` running a script.

> [interested] Want a message in your team chat every time someone publishes? Or a build kicked off?
>
> Go to Admin, Fixing, Webhooks. Paste in an address, pick which events you care about, like published changes or new claims, and save. Hit Send a test to check it arrives.
>
> Every delivery is signed with a secret, so your end can check it really came from your server.
>
> If you'd rather just run a script, use `mp watch` on any machine that's signed in. Give it a project, an event and a command, and it runs your command each time that happens.

**Callouts:** ring on *Webhooks*. Spot on the event list. Ring on *Send a test*. Code on the `mp watch` line, tagged "Runs your script".

---

## S8. Build machines and the command line

**On screen:** `mp login`, `mp get-latest`, the `--json` output, then `mp mcp` in an assistant's settings.

> [matter-of-fact] Artists get the app. Build machines get `mp`.
>
> Log in once with `mp login` and your server address. Then it's the same ideas as the app: get latest, claim, publish, all from scripts.
>
> If you're used to Perforce, the old words work too, like sync and submit. And add `--json` to anything when a script needs to read the output.
>
> [curious] One more: `mp mcp`. It lets an AI assistant like Claude look at your project, find files, read the history and see who has what claimed. Handy for "who touched the forge last week?"

**Callouts:** code on `mp login`. Tag "sync = get latest" next to the alias. Code on `--json`. Spot on the `mp mcp` config.
